01 · 프로젝트 개요

InterviewIQ란?

혼자서도 모의 면접을 진행하고, 답변 내용과 비언어 행동을 함께 분석받는 실시간 멀티모달 면접 코칭 서비스

핵심 차별점

  • 최종 답변만 평가하지 않고, 면접 중 데이터를 5초 chunk로 저장·분석
  • 웹캠 전신 비언어 + 마이크 음성 + STT 텍스트를 chunkId 기준 병합
  • 답변 단위(answer turn)로 묶어 꼬리질문/리포트 생성

02 · 기존 계획 방향

0521 ACTION_PLAN, PROJECT_CONTEXT 기준의 기존 설계

서비스 컨셉

  • 한 번의 모의 면접을 진행하고, 답변 내용·비언어·음성을 분석

03 · 오늘 회의 (2026-05-25)

방향 전환: 교정 루프

첫 면접을 개인 baseline으로 저장하고, 이후 면접과 비교해 변화를 보여주는 코칭 구조

한 줄 정의

AI가 절대 평가를 하는 면접관이 아니라, 사용자 본인의 초기 상태와 비교해 시선 이탈·긴 침묵·자세 흔들림·답변 구체성이 어떻게 변했는지 보여주는 서비스.

새 흐름

온보딩
→
Baseline 면접
→
요약 지표 저장
→
교정 포인트 제시
→
Correction Loop
→
변화 비교 리포트

왜 좋은가

  • AI 절대 평가 신뢰도 문제 회피
  • "본인 대비 변화"라 설명이 안전
  • 발표에서 그래프/수치로 보여주기 좋음

기술 정당성 강화

  • MediaPipe → baseline·loop 동일 측정
  • Web Audio → 침묵/음량 비교
  • STT → transcript 비교 + 피드백

주의할 점

  • 질문이 달라지면 비교가 공정하지 않음
  • 답변을 외워 개선처럼 보일 수 있음
  • 지표 ≠ 실제 면접 역량 (단정 금지)
04 · Before / After

무엇이 어떻게 바뀌었나

구조를 갈아엎는 것이 아니라, 기존 chunk·STT·RAG·LangGraph 위에 baseline + 교정 루프 레이어를 얹는 변화

구분 BEFORE — 기존 방향 AFTER — 회의 후 새 방향
서비스 컨셉 한 번의 면접을 분석해 다음 질문/최종 피드백 제공 여러 회차를 비교해 사용자의 변화·개선 추세를 보여줌
평가 기준 현재 답변이 얼마나 적절한지 (절대 평가) 초기 baseline 대비 얼마나 변화했는지 (상대 비교)
사용자 경험 면접 1회 → 결과 확인 → 종료 연습 → 피드백 → 목표 선택 → 재연습 → 변화 확인 반복
최종 결과물 개별 면접 리포트 개별 리포트 + 회차별 비교 + 남은 약점 요약
세션 모델 session만 존재 sessionType: baseline | practice_loop, loopIndex, baselineSessionId 추가
LLM 입력 chunk·STT 원문을 그대로 길게 넣을 위험 Write/Select/Compress/Isolate로 baseline 요약·현재 목표만 선별 입력
발표 스토리 "멀티모달 기술을 다 썼다" "개인 기준선 대비 무엇이 좋아졌는지 시각화한다"

06 · 세션 연결 방식

로그인 없이, groupId로 묶는다

baseline → loop → report를 "한 세션"이 아니라 "같은 그룹의 여러 세션"으로 연결. 끊겨도 안 죽음.

핵심 결정

  • baseline + loop×3 을 한 세션으로 묶지 않음 (끊기면 다 날아감)
  • 변수/메모리 저장 X · Redis 영속 저장 O
  • 로그인 없이 groupId + localStorage로 사용자 구분
  • "사용자 = 같은 브라우저에서 같은 groupId를 들고 오는 사람"

왜 이렇게?

  • 변수 저장은 서버 재시작·worker 분리에 취약
  • 한 세션 = 30~60분 → 시연·연습에서 끊김 리스크 큼
  • 로그인 구현은 2주 일정에 비용 대비 효과 낮음
  • Redis는 chunk 병합용으로 이미 쓰는 인프라 — 추가 비용 0

흐름

1. "면접 시작" 클릭
   → 백엔드: groupId = "g_a1b2c3" 발급
   → 프론트: localStorage.setItem('groupId', 'g_a1b2c3')

2. baseline 면접 종료
   → Redis: SET group:g_a1b2c3:baseline {gazeAway:0.38, ...} EX 7d

3. "교정 루프 시작" 클릭 (브라우저 껐다 켜도 OK)
   → 프론트: localStorage에서 groupId 꺼냄
   → POST /sessions/loop { groupId }
   → 백엔드: Redis에서 baseline 조회 → 동일 측정

4. loop 종료 → 비교 리포트
   → baseline + 이번 loop 요약 비교

가능한 것

  • baseline 끝내고 브라우저 꺼도 다음 날 이어서 가능
  • 서버 재시작에도 데이터 유지
  • worker 여러 개여도 동일 데이터 조회

제약

  • 같은 노트북 · 같은 브라우저 · 같은 도메인이어야 함
  • 시크릿 모드 X · 브라우저 데이터 삭제 X
  • Redis TTL 만료 시 새로 시작 (기본 7일 권장)
  • 시연 당일은 연속 진행이라 사실상 무관

Backend

  • 세션 모델에 sessionType, loopIndex, baselineSessionId 추가

Frontend / MediaPipe

  • baseline / loop 모드 분기 UI

  • 같은 측정 파이프라인 유지 (공정성)
  • "교정 포인트" 안내 컴포넌트
